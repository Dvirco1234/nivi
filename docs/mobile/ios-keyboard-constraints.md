# iOS Keyboard Extension — Hard Platform Constraints (Fact-Sheet)

Research date: 2026-07-26. Goal: verify whether a whisper.cpp-quality offline
Hebrew dictation keyboard is feasible as a Custom Keyboard Extension on iPhone.

Status legend: **verified** / **partly verified** / **unverified**.

---

## 1. Custom keyboard extension memory limit

- Finding: Dvir's ~60-80MB estimate is directionally correct but the real number is **not a single published constant** — Apple has never documented an exact figure for `Custom Keyboard` extensions. Empirical reports from developers cluster in a **30-80MB band**, and it appears to vary by device RAM and iOS version (jetsam per-process limits scale with total device memory). Concrete data points found:
  - React Native GitHub issue: keyboard crashes reported at **48MB** (older iOS, exact version unclear from search snippet).
  - iOS 17 beta: a *Widget* extension (different extension type, cited for context) hit its jetsam limit around **30MB**.
  - One dev blog cites keyboard extension crashing once total memory after allocation exceeds **~77MB**, with a memory-warning callback firing around 70% of that (~54MB).
  - General app-extension guidance: only extension types with **>100MB** limits (e.g. Share Extension ~120MB) are considered safe for heavier frameworks; Custom Keyboard is explicitly called out as one of the more constrained types.
  - No official Apple developer-documentation page states a hard byte number for keyboard extensions (checked App Extension Programming Guide — it describes the *sandbox* restrictions, not a memory figure).
- Number: **~30-80MB, device/iOS-version dependent** (not a single fixed constant). Treat ~60MB as a reasonably safe design ceiling; ~48MB as the well-attested crash point on constrained configurations.
- Changed across iOS 17/18/26?: No source found that documents a specific historical change to the keyboard-extension limit across iOS 17/18/26. **Unverified** whether it changed recently — Apple does not publish a changelog for this.
- Behavior on exceeding (jetsam): Confirmed — exceeding the limit causes an immediate **jetsam OOM kill** of the extension process (no graceful degradation), consistent with how jetsam works for all iOS extension types.
- Source(s): [React Native GH issue #31910](https://github.com/facebook/react-native/issues/31910) (48MB crash reports); [Apple Dev Forums: iOS 17 Beta 3 Widget Extension 30MB limit](https://developer.apple.com/forums/thread/733347); [Apple Dev Forums: File Provider Extension 20MB limit thread](https://developer.apple.com/forums/thread/804378) (context for extension memory limits generally being small and type-specific); [Fleksy blog: Limitations of custom keyboards on iOS](https://www.fleksy.com/blog/limitations-of-custom-keyboards-on-ios/); [Medium: CoreText Emoji Memory Retention in SwiftKey Keyboard Extension](https://medium.com/@mohasalah/from-2014-to-now-fixing-coretext-emoji-glyphs-memory-retention-on-ios-1c6a227d592d) (77MB crash / ~54MB warning figures). Apple's own [App Extension Programming Guide: Custom Keyboard](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/CustomKeyboard.html) does not state a number.
- Confidence: **partly verified** — the order of magnitude (tens of MB, well under 100MB) is solidly corroborated by multiple independent sources; the exact figure and any recent-iOS change are unverified.
- Architecture implication: A ~1.6GB whisper-large-v3-turbo GGML model (or any multi-hundred-MB model) **cannot load inside the keyboard extension process** under any of the reported limits. Confirms Dvir's premise that in-extension inference is off the table — the model must run in the host app (or a separate process), with the keyboard extension acting only as a thin trigger/UI + text-insertion surface.

## 2. Microphone access from a keyboard extension

- Finding: **Dvir's implicit assumption that a keyboard extension could record mic audio directly is wrong — confirmed by a hard OS-level entitlement block, not just an App Review policy.** A developer who enabled `RequestsOpenAccess` and attempted `AVAudioSession`/recording got the explicit system error: `CMSUtility_IsAllowedToStartRecording: ... was NOT allowed to start recording because it is an extension and doesn't have entitlements to record audio.` This is enforced by coreaudiod/CMS, independent of Full Access — no plist key or entitlement grants it. This matches a second independent forum thread reporting the same wall.
- Does AVAudioEngine/AVAudioSession work in a keyboard extension?: The session/engine objects can be *instantiated*, but **actually starting recording is refused by the OS** for any process of type "extension" — this is a categorical block on the App Extension process class, not something Full Access lifts.
- What does RequestsOpenAccess (Full Access) unlocks?: Per Apple's App Extension Programming Guide and corroborating sources: network access, iCloud, Location Services, Photos/Address Book access, sharing data with the containing app (App Group), Game Center / In-App Purchase via the containing app. **Microphone recording is not in this list and is not unlocked by Full Access** — confirmed both by the documented capability list and by the reproduced runtime error above.
- Real App Store dictation keyboards doing on-device recording — how do they do it?: They don't record from inside the extension. The pattern found (matches what "Wispr Flow"-style keyboards reportedly do, per an unanswered Sept-2025 Apple Developer Forums thread) is: keyboard extension shows a mic button → tapping it triggers/deep-links the **containing host app** → the host app (a normal foreground/backgrounded app, which *does* have mic entitlements) performs the actual recording + transcription → result is written to a shared **App Group** container → the keyboard extension reads/polls the result and calls `textDocumentProxy.insertText(...)` to insert it. This requires bouncing to the host app, which is exactly the friction Dvir wants to avoid — no counter-example of a keyboard doing true in-place seamless recording was found.
- Source(s): [Apple Dev Forums: Recording audio in keyboard extension (CMSUtility error)](https://developer.apple.com/forums/thread/742601); [Apple Dev Forums: Record microphone in a Keyboard app (in the background), Sept 2025, unanswered](https://developer.apple.com/forums/thread/800500); [Apple Dev Forums: AVAudioSession setActive throws error 561015905 in Keyboard Extension](https://developer.apple.com/forums/thread/709107); [Medium: Limitations of custom iOS keyboards](https://medium.com/@inFullMobile/limitations-of-custom-ios-keyboards-3be88dfb694); Apple [App Extension Programming Guide: Custom Keyboard](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/CustomKeyboard.html) (Full Access capability list).
- Confidence: **verified** that direct mic recording from within a keyboard extension is blocked at the OS entitlement level, reproduced via an explicit system error message in two independent developer reports. The exact wording/behavior could shift in future iOS versions but the architectural fact (extensions as a process class cannot record audio) is Apple's documented sandbox model, not a bug.
- Architecture implication: **This is the second constraint that forces the "trigger extension + host app records" architecture** — even if the whisper model ran outside the extension (e.g. in the host app), the extension itself still cannot capture microphone audio. Any seamless-recording design must have the *host app* (not the extension) own the `AVAudioSession`/`AVAudioEngine`, which raises the IPC and backgrounding questions in section 3.

## 3. Extension <-> host-app IPC

- Finding: A **shared App Group container is the real IPC mechanism used in practice**, but it is not primarily a live "socket" channel — it's mostly file/UserDefaults-based handoff plus URL-scheme launch, because the host app usually is *not running* when the keyboard is active. The pattern repeatedly found: keyboard extension calls `extensionContext.open(URL(string: "myapp://dictation")!)` to **launch/foreground the host app**, the host app then does the actual mic recording via `AVAudioEngine`, writes the transcript into the App Group container, and signals completion back via a **Darwin notification** (`CFNotificationCenter`, cross-process) or the keyboard polls the shared file/UserDefaults. This requires a visible app switch, not a silent background hand-off.
- Local socket / loopback via App Group — works on current iOS?: Technically, Unix domain sockets placed inside an App Group container directory **do work** between processes of the same team (confirmed for macOS by an Apple DTS engineer on the forums; the same App Group container mechanism exists on iOS). However Apple's own guidance is to **prefer XPC or higher-level shared-container patterns over raw UDS**, and no iOS-specific confirmation of a live keyboard-extension↔host-app socket was found — the real-world pattern developers actually ship uses `extensionContext.open(URL)` + Darwin notifications + shared file, not a persistent socket, precisely because the host app isn't guaranteed to be running to have a listening socket open.
- What keeps host app alive (background audio mode)?: `UIBackgroundModes: audio` combined with an active `AVAudioSession`/`AVAudioEngine` recording session is the standard technique to keep an iOS app alive in the background rather than suspended within seconds — same mechanism voice-memo/call-recording apps use. But it only helps *after* the host app has been launched into the foreground once (via the extension's `open(URL:)` call); it does not let the host app run persistently from a cold/suspended state, and iOS still applies scrutiny/kill to background-audio apps not genuinely using the mic.
- Reliability / real-world evidence: An unanswered Sept-2025 Apple Developer Forums thread from a developer explicitly attempting this exact "Wispr-Flow-style" architecture (keyboard extension → open host app → record → App Group → insert text) shows this is a **live, unsolved pain point for real developers right now**, not a settled recipe. No forbidding statement from Apple was found, but no confirmed robust production recipe either. A separate thread reports extension-side sockets becoming unresponsive after the lock screen, suggesting persistent-socket approaches are fragile across suspend/resume.
- Source(s): [Apple Dev Forums: network extension, app groups, unix domain socket](https://developer.apple.com/forums/thread/133543) (macOS-focused; UDS via App Group confirmed possible, XPC preferred); [Apple Dev Forums: Record microphone in a Keyboard app (in the background), Sept 2025](https://developer.apple.com/forums/thread/800500) (the exact architecture, unanswered); [Damien Deville: Interprocess communication on iOS with Berkeley sockets](https://ddeville.me/2015/02/interprocess-communication-on-ios-with-berkeley-sockets/); [Apple Dev Forums: Socket Becomes Unresponsive in Local Connectivity Extension After Lock Screen](https://developer.apple.com/forums/thread/778447).
- Confidence: **partly verified**. The App-Group-based handoff pattern (open URL → host app records → write to shared container → Darwin notification/poll → keyboard inserts text) is well corroborated. Whether a **persistent low-latency socket** connection stays reliable is **unverified** — evidence points the other way.
- Architecture implication: Confirms this cannot be a silent background hand-off — the current best-known pattern **requires visibly switching to the host app** to record. No evidence was found of any app achieving truly seamless (no app-switch) on-device recording triggered from a keyboard extension; this is the crux blocker for the "seamless in every app" goal, independent of the whisper-model-size question.

## 4. Sideloading a keyboard extension

- Finding: Both free and paid routes technically support sideloading an app + its keyboard extension, but the free route has real friction for an actively-developed daily-driver app.
- Free Apple ID (7-day) vs paid ($99/yr): device limits:
  - **Free Apple ID**: apps must be **re-signed every 7 days** (they stop launching after expiry), a cap of **3 apps installed at a time** per free account, and roughly **10 new App IDs per 7-day rolling window** — and an app extension (e.g. the keyboard) **consumes its own App ID from that same 10/week pool**, on top of the host app's App ID. No push notifications, no in-app purchases. Device registration for free accounts is limited (commonly cited as ~3 devices).
  - **Paid $99/yr Apple Developer Program**: up to **100 devices/year** registered per platform, apps/provisioning valid for **1 year** instead of 7 days, no practical 3-app cap, and the weekly App ID churn issue disappears since you're not constantly re-creating IDs.
- Do app extensions sideload fine?: Yes — app extensions (including custom keyboards) sideload as part of their containing app's bundle like any other extension; no source found suggesting Apple technically blocks sideloaded keyboard extensions from functioning once installed and enabled in Settings.
- Keyboard-specific gotchas: The main practical gotcha isn't keyboard-specific technically, it's the **7-day re-sign cycle on free accounts** — a keyboard extension that stops working every week (until re-signed via Xcode/AltStore/Sidestore reconnect) is a poor daily-driver experience, and each re-sign after the free weekly App-ID budget is exhausted can hit the 10-App-ID/week ceiling faster than a plain app because the extension itself counts separately. This makes the **paid $99/yr account the practical requirement** for a daily-use personal keyboard, not a hard technical wall on the free tier.
- Source(s): [Hacker News thread confirming free Apple ID sideloading basics](https://news.ycombinator.com/item?id=36023322); [Apple: Choosing a Membership](https://developer.apple.com/support/compare-memberships/); [Apple Dev Forums: Limits on App IDs - 10 every 7 days](https://developer.apple.com/forums/thread/675347); [Apple Dev Forums: "maximum App ID limit" problem](https://developer.apple.com/forums/thread/701805); [SideStore Docs FAQ](https://docs.sidestore.io/docs/faq); [dev.to: How iOS Sideloading Actually Works in 2025](https://dev.to/1_king_0b1e1f8bfe6d1/how-ios-sideloading-actually-works-in-2025-dev-certs-altstore-and-the-eu-exception-1m2h).
- Confidence: **verified** for the core numbers (7-day expiry, 3-app cap, 10 App IDs/week on free; 100 devices, 1-year validity on paid $99/yr) — these are consistent across multiple independent sources including Apple's own comparison page. The claim that extensions consume their own App-ID slot is **partly verified** (stated in secondary sources, not found spelled out on an Apple page, but consistent with how App IDs work per-target).
- Architecture implication: Not a blocker either way, but confirms the project should just budget the **$99/yr Apple Developer Program** from day one rather than free-tier sideloading — avoids the 7-day-expiry churn that would otherwise fight against "seamless daily use," and is cheap relative to the effort involved.

## Summary / verdict

Dvir's core assertions were **directionally right on the memory number but wrong on the mechanism** — the real blocker isn't primarily "the model is too big for the sandbox," it's that **the keyboard extension cannot record audio at all**, by OS-level entitlement, regardless of memory budget or Full Access.

1. Memory limit: **~30-80MB, not a single fixed constant** — Dvir's 60-80MB guess is in the right ballpark but there's no official documented number, and it may be as low as ~48MB on constrained configs. **Partly verified.** Either way, a 1.6GB whisper model cannot run in-extension — confirmed.
2. Mic access: **Keyboard extensions cannot record audio, period** — not "Full Access unlocks mic," but a hard OS-level block reproduced via an explicit system error (`CMSUtility_IsAllowedToStartRecording... doesn't have entitlements to record audio`). This is the single most important correction to Dvir's mental model. **Verified.**
3. IPC: App Group + Darwin notifications/shared file **does work** as a handoff mechanism, but the standard pattern **requires visibly opening the host app** (`extensionContext.open(URL:)`) — no evidence of a way to record audio from a backgrounded/suspended host app triggered invisibly from the keyboard. This reproduces the exact "bounce to the app" friction Dvir is trying to eliminate; it is not solved in any source found. **Partly verified**, and this is the finding most likely to be the real architecture-killer.
4. Sideloading: Free tier works but with weekly re-sign churn that's impractical for daily use; the **$99/yr Apple Developer Program is the practical requirement** — it removes 7-day expiry and the 3-app cap. **Verified**, and not a blocker either way.

**Bottom line implication for the architecture**: because a keyboard extension can never capture microphone audio itself (finding 2, verified) and the documented handoff pattern requires an app switch (finding 3), a truly "seamless in every app, no switch" whisper-quality dictation keyboard on iPhone is **not achievable with a Custom Keyboard Extension as currently understood from public documentation and developer reports** — the best achievable UX under today's constraints is "tap the mic key → brief bounce to host app → auto-return," which is closer to what the existing App Store competitors already do than Dvir's stated goal. If a lower-friction path exists, it would have to rely on either (a) accepting a one-time visible app switch per dictation (minimizing its cost via background audio mode + fast auto-return), or (b) exploring whether Apple's own Dictation/SpeechKit customization surfaces (not investigated in this pass) offer any hook for injecting a custom model — this was outside the scope of the 4 questions asked and is flagged as a possible next research thread, not something this fact-sheet confirms or refutes.
